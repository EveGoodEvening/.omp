# User Instructions

- When you learn something reusable while working in a project, record it in the `Lessons` section of the repo-level `AGENTS.md` at the repository root. This includes library versions, model names, project conventions, corrected assumptions, and fixes for mistakes. Do not write these lessons to the user-level global files under `~/.omp/agent/`.
- Docker-published Compose ports can bypass expected UFW `deny incoming` behavior through Docker iptables chains; local/dev service ports should bind explicitly to `127.0.0.1` in `ports` mappings on cloud hosts unl
ess public exposure is intended.

## Shared resource limits

- Memory is a shared, finite machine resource. An OOM can terminate the entire session and its agents. Agent-count limits and per-project locks are not memory limits: independent projects, sessions, Claude and OMP all compete for the same RAM. Enforce limits at process launch, not just in prompts.
- Run every memory-heavy command through `~/.omp/bin/heavy-gate [-n N] [-m 6G] -- <cmd>`. It shares `/tmp/heavy-gate` with Claude: at most 2 slots, MemAvailable >= 4500 MiB before launch, and a separate systemd scope with MemoryMax (default 6G) and no swap. If resource isolation is unavailable, stop; never run uncapped. Do not override the shared directory or limits to evade the gate.
- Heavy includes every browser launch (Playwright/Puppeteer/Selenium, screenshot/smoke/e2e scripts, even with a project gate), Electron, emulators, and any process expected to exceed about 2 GiB. `-n N` reserves N browser slots; prefer one browser and `--workers=1`, reusing its context/page. Close browsers in `finally`; do not add another per-project lock.
- The gate waits, possibly for minutes. For finite gated commands use OMP `bash` with `async: true, timeout: 0`: async alone does not disable the execution deadline. Never wrap the gate in `timeout`. Use `~/.omp/bin/heavy-gate --status` to inspect holders. A busy slot after the main command exits can mean descendants are still alive; terminate only processes/scopes you own.
- `agent/extensions/heavy-gate.ts` invokes `~/.omp/bin/heavy-gate-hook` before Bash and Eval execution. When denied, run the work under the gate; never disguise the command or switch tools to bypass it. Detection is best-effort, not a sandbox: indirect/dynamic launches and third-party extensions may be invisible, and the gate rule still applies.
- OMP's Eval `browser.open()` is an internal bridge, not a tool-call event. Do not use it to start an unmanaged browser (`app.path` or implicit managed Chromium). Launch browser work under the gate as an external script, or explicitly attach to a browser already launched under the gate using `app.cdp_url`; an existing user-owned `app.relay: true` browser is also allowed. Put the explicit `app` argument first in `browser.open` so the launch guard can recognize attach-only calls. A CDP connection is not proof of a gate: ensure the local browser is gated, close the tab, and stop your owned browser when finished. Never wrap the whole OMP session in a memory-capped gate.
- Before fan-out, check `free -m` and `~/.omp/bin/heavy-gate --status`. Treat browser verification as one machine-wide stage of width <= 2, shared with other sessions: use batches of at most two or one serial verifier, never a wide browser `parallel()`/workpool. Give other agents static checks and unit tests. Include these gate, timeout, and browser-attachment rules in every browser-capable subagent's prompt; extension inheritance is not a substitute for explicit orchestration instructions.
- Apply the same launch-time lock/check principle to other shared finite resources: ports, GPUs, and development servers used by other agents. A headcount rule in a prompt is not a resource guard.
